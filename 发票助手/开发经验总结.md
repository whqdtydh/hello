# 开发经验总结 —— 发票助手项目全周期复盘

> 复盘范围：从 2026-08-14 立项到 WebView2 改造 + OCR 收编完成（全周期 40+ 次提交）
> 核心结论：**先谈功能性，再谈落地。** 技术选型服务于功能，不被技术方案绑架。

---

## 一、项目概述

**要解决的问题**：用户每周要从 QQ 邮箱里把各类电子发票（打车、高铁、ETC、商家开票等）下载归类，纯手工操作繁琐。
**验收标准**：打开程序 → 扫码登录一次 → 左侧网页勾选邮件 → 点下载 → 发票 PDF 自动命名（金额+日期+类型）归档到本地目录，会话持久化二次免登录。

## 二、功能演进时间线（全周期）

### 阶段 1：立项与早期功能（8/14 - 8/17）
- Initial commit → 基本骨架：QQ 邮箱内嵌登录、邮件勾选、附件下载
- **早期关键决策**：内嵌浏览器选了 **QtWebEngine**（当时"能用"，为后续体积问题埋雷）
- 第一次轻量化尝试（1bee58e/e635221）：裁剪翻译包、QML 插件、devtools——**只治标不治本，Qt6WebEngineCore.dll 195MB 仍在**

### 阶段 2：勾选识别攻坚（8/17 - 8/18，最痛的阶段）
连续 **12 次提交**反复试错，这个阶段的教训最深刻：

| 尝试 | 结果 |
|---|---|
| MutationObserver 精确监听 | 误识别 → 推翻 |
| 全 API 模式（Python 内存管理勾选） | 与用户"在网页里勾选"的使用习惯冲突 → 回退 |
| click 延迟校验 + DOM 扫描 | 补漏但复杂，维护成本高 |
| 最终方案 | **API 列表 + 程序内勾选（Python 内存），移除网页 DOM 监听依赖** + 界面简化为"左侧邮箱网页 + 右侧操作区" |

**教训**：勾选识别的本质是**功能定义不清晰**（"勾选"到底发生在网页还是程序里？用户习惯是什么？）——功能没定清楚就反复改技术实现，是最大的时间黑洞。**如果一开始先问清楚"用户期望的勾选交互"，这 12 轮试错可以压缩到 1-2 轮。**

### 阶段 3：下载体验优化（8/19 上午）
- 并发下载（邮件 3 worker + 附件 6 worker）+ 边拉边处理
- 边勾边读：勾选瞬间 JS 上报 mailid → 后台预读器缓存详情（**这是性能优化的正确姿势：先有功能，再按用户操作路径优化）**
- 结果树日志迭代 6 轮（总结置顶、折叠、复制、类型分布）
- 金额/日期提取攻坚：票面优先（价税合计→小写→合计→票价）、行程单"X至X"日期规则、未识别标注

### 阶段 4：正式任务体系（用户批准 3→5→1→2→6）
| 任务 | 内容 | 成果 |
|---|---|---|
| 任务 3 | 下载链路加固 | 限流信号量、原子落盘（.part+sha256+内容校验）、失败分类指数退避 |
| 任务 5 | 模块拆分 | 纯函数化（archive_service/pdf_service），api_downloader 1395→1225 行 |
| 任务 1 | SQLite 任务状态机 | mails/files/archives 三表，崩溃恢复、幂等去重、提取率审计 |
| 任务 2 | 识别率提升 | OCR 降级（RapidOCR）+ 规则配置化热更新 |
| 任务 6b | 自动更新 | GitHub Releases 检查/下载/sha256/原子替换重启+回滚 |
| 任务 6a | 打包发版 | **暴露 500MB 问题**，spec 过滤省 52MB，build.ps1 一键发版 |

### 阶段 5：WebView2 架构演进（8/19 下午）
- 500MB 中 QtWebEngine 占 195MB → 用户决策换 WebView2 系统内核
- P0（能力验证）→ P0'（嵌入验证）→ 正式改造 → 排障（假导航/addScript 失效/单调试器）→ 完成
- 体积 500 → ~250MB（预期），UI 零改动

### 阶段 6：OCR 收编
- rapidocr_onnxruntime → `app/engine/ocr_light/`（代码自有化，保留 Apache-2.0）

## 三、核心经验（按主题提炼）

### 1. 功能先行（本次最大教训）
- 勾选识别 12 轮试错 = 功能未定就写实现的代价
- **正确顺序**：功能定义（勾选发生在哪、用户习惯）→ 交互确认 → 技术实现
- 架构替换（WebView2）反而是"功能明确"后的干净案例：目标清晰（UI 零改动、体积减半），两轮 POC 就落地

### 2. 技术选型要为功能服务
- QtWebEngine 选型时只看了"能不能内嵌"，没问"体积是不是约束" → 后期整体替换
- **选型清单应包含功能约束项**：体积、启动速度、部署环境、用户机器条件
- 技术方案与功能冲突（全 API 模式 vs 网页勾选习惯）→ 回到功能层重新定，而不是硬推技术方案

### 3. POC 先行验证（架构演进的标准姿势）
```
明确目标 → P0 能力验证（最小 demo）→ P0' 集成验证 → 分步改造 → 测试护航
```
- 新引擎 API 与旧版对齐（run_js/cookies...），调用方零改动，回归成本极低
- 独立文件不侵入（web_client_wv2.py 与旧版并存），随时可回退

### 4. 体积与打包（落地阶段必查）
- **体积要早算**：功能设计阶段就应明确目标，让选型为之服务
- 大文件拆着看：按目录/文件聚合分析，一眼定位大头
- **PyInstaller 收集陷阱**：函数内 import、类型注解里的 import 都会拖"全家桶"进包（残留 `QWebEnginePage` 引用 = 白亏 195MB）；清理残留引用是真实的体积优化

### 5. 性能优化要沿用户路径
- 边勾边读（预读器）比盲目提高并发更有效——**先分析用户操作序列，再优化瓶颈**
- 每一步优化都留日志（每封耗时/总耗时），用数据定位瓶颈而非拍脑袋

### 6. 稳定性优先
- 下载加固（原子落盘+校验+退避）比"多下几封"重要
- 崩溃恢复（SQLite 状态机）让长任务可中断可续跑
- 自动更新必须带回滚

### 7. 测试护航
- 97 → 101 → 105 测试随功能增长，**每次改动跑全量**，架构替换全程零回归
- 纯函数化（任务 5）让测试成本直线下降——**能拆成纯函数的逻辑就不要埋在 GUI/副作用里**

### 8. 流程纪律
- push 前同步 README；提交信息结构化；产物（build/dist/日志）不入库；架构改动走独立分支

## 四、WebView2/CDP 实战坑位（踩过即经验）

| 坑 | 现象 | 解法 |
|---|---|---|
| Page.navigate 假导航 | target 元数据更新、页面 href 不变 | 原生 `Navigate()` API |
| addScriptToEvaluateOnNewDocument 失效 | WebView2 只支持 CDP 子集 | 原生 `AddScriptToExecuteOnDocumentCreatedAsync` |
| 单调试器限制 | probe 脚本踢断主连接 → 表现为"下载不了" | CDP 断线自动重连 + 脚本源重放 |
| WebSocket 握手 403 | 新版 Chromium 拒绝带 Origin 握手 | `suppress_origin=True` |
| 端口就绪时序 | GUI 线程等端口 14 秒 → 窗口未响应 | 宿主层预等端口就绪 |
| pywebview 端口参数 | 环境变量被显式设置覆盖 | `webview.settings['REMOTE_DEBUGGING_PORT']` |

**调试方法论**：独立 probe 脚本（连 CDP 手动导航/注入/查状态）比在主程序里盲试快得多。

## 六、铁律（用户强制，长期生效）

1. **先谈功能性，再谈落地**——功能需求与验收标准确认前，严禁写代码/选型。
2. 技术选型服务于功能；方案与功能冲突时回到功能层重新讨论。
3. 落地阶段的体积、性能、部署约束要在**功能定义时**就纳入讨论，而不是等实现完才发现。
